# webbot

日本語Wikipediaを検索し、見つけた文章を読んで質問に答える小さな言語モデル(RAG)を、トークナイザーからすべて自前で実装するプロジェクトです。LLM自作シリーズの3作目です。

## 概要

- **検索→読む→答える**: ローカルに置いたWikipediaの段落を検索し、取り出した段落から答えを抜き出して回答するモデルを目指します
- **データ**: 文書は [hpprc/jawiki](https://huggingface.co/datasets/hpprc/jawiki)(段落単位の日本語Wikipedia、CC BY-SA 3.0 / GFDL)、学習用のQAは [cl-nagoya/auto-wiki-qa](https://huggingface.co/datasets/cl-nagoya/auto-wiki-qa)(同じWikipediaから生成された質問・答え・根拠段落、CC BY-SA 4.0)、評価は [JSQuAD](https://github.com/yahoojapan/JGLUE)(CC BY-SA 4.0)を使う予定です
- **CPUのみ**で学習できる規模を前提にしています

### トークナイザー

3種類あります。どちらも同じ事前トークン化と同じ特殊トークンを使い、`train` / `encode` / `decode` / `save` / `load` の使い方も共通です。`len(tok)` は特殊トークンを含めた語彙数で、モデルの埋め込みの行数になります。

- **事前トークン化**: 日本語に対応しています。ひらがな・カタカナ・漢字・英字・数字・記号といった文字種の境目で分割し、ピース(トークン)がこの境目をまたぐことはありません
- **特殊トークン**は8個あり、通常の語彙の直後に次の順でIDを振ります。`vocab_size` は、特殊トークンを含めた語彙の総数です

  | トークン | 役割 |
  |---|---|
  | `<\|endoftext\|>` | 文書の区切り、回答の終わり |
  | `<\|pad\|>` | バッチの詰め物 |
  | `<\|question\|>` | 質問の始まり |
  | `<\|search\|>` 〜 `<\|/search\|>` | モデルが書く検索語 |
  | `<\|doc\|>` 〜 `<\|/doc\|>` | 検索で取り出した段落(1件ずつ) |
  | `<\|answer\|>` | 回答の始まり |

  想定している並びは `<|question|>質問<|search|>検索語<|/search|><|doc|>段落<|/doc|>…<|answer|>回答<|endoftext|>` です。特殊IDにするのは `encode(text, allowed_special=...)` で許可したトークンだけです。Wikipedia本文などに同じ文字列が出てきても、普通の文字としてエンコードします

#### BPE(`BPETokenizer`)

- GPT-2方式のバイトレベルBPEです
- 学習には2つの実装があり、`BPETokenizer(backend=...)` で選べます。既定の `"auto"` は、Rust版が入っていればRust版を使います
  - `"python"`: 参照実装。ペア頻度を差分更新し、ヒープは遅延削除方式です
  - `"rust"`: 同じ手順をRustで実装したものです。差分更新は、マージした位置の前後のペアだけを更新します
- 両者は、同点の決め方(記号の文字列の辞書順で大きい方を優先)まで含めて同じマージ列を出します
- エンコードもRust版があり、単語単位のキャッシュを持ちます。事前トークン化(正規表現)はPythonのままです
- テストでは、学習結果を「マージごとに全ペアを数え直す素朴な実装」と、Rust版の学習とエンコードの結果を「Python版」と、それぞれ完全一致で比べています

#### Unigram言語モデル(`UnigramTokenizer`)

- Kudo (2018) の方式で、SentencePieceの `unigram` に当たります。各単語を「ピースの対数確率の和が最大になる分割」で区切ります(Viterbi)
- 学習の流れ
  1. 頻出の部分文字列(最大16文字、「頻度×長さ」の上位100万個)から、大きな候補語彙を作ります
  2. EMでピースの確率を推定し直します。前向き・後ろ向きアルゴリズムで期待出現回数を求め、M-stepは最尤推定です
  3. 除いても尤度が下がりにくいピースから25%ずつ刈り込みます。損失の近似はSentencePieceと同じです
  4. 2と3を、予算の1.1倍以下になるまで繰り返します。最後に確率の高い順に予算まで残します
- **文字単位**で扱います。出現の99.95%をカバーする文字は必ず語彙に残し、それ以外のまれな文字はUTF-8のバイト(ID 0〜255)に分解します(バイトフォールバック)。どんな文字列も元に戻せます
- コーパスが小さく候補が予算に届かない場合、語彙は `vocab_size` より小さくなります
- テストでは、ViterbiとEMの期待出現回数を「全分割の列挙」と比べています。ほかに、EMで尤度が下がらないこと、使われないピースから先に刈り込まれること、予算がぎりぎりでも必須文字が残ることを確かめています

#### WordPiece(`WordPieceTokenizer`)

- BERTの方式です。学習はBPEと同じく隣り合う記号のペアをマージしますが、選ぶ基準は「ペアの出現回数 ÷ (左の記号の出現回数 × 右の記号の出現回数)」が最大のペアです
- 単語の2文字目以降のピースは、`##` 付きの別トークン(「の」と「##の」)です。内部では `(続きかどうか, 文字列)` の組で持つので、本文に `#` が含まれても曖昧になりません
- エンコードは、マージを再生するのではなく、単語の先頭から最長一致を貪欲に取ります
- 文字のカバー率とバイトフォールバックは、Unigramと同じ扱いです。カバー率の外にある文字は、マージの壁になります
- **ペアの最低出現回数**(`train(..., min_pair_count=100)`): 出現回数がこの回数に満たないペアはマージしません。標準のスコアだけでは、日本語Wikipediaでは珍しい漢字の組ばかりがマージされ、ほぼ文字単位になるためです(下の比較)。`min_pair_count=1` で標準のWordPieceになります。出現回数はマージのたびに変わるので、出現回数が変わってスコアを付け直すときに、回数が下限以上のペアだけを候補のヒープに入れます
- 学習はPythonのみで、ペア数の差分更新と遅延削除ヒープを使います。マージで出現回数が減った記号を含むペアは、スコアを計算し直します
- テストでは、マージ列を「毎回全部数え直す素朴な実装」と、最低出現回数を1・3・10回にした場合も含めて完全一致で比べています。ほかに、出現回数ではなくスコアで選ぶこと、下限で珍しいペアが外れること、マージの結果できたペアが下限を超えると候補になること、各位置で最長一致を取ることを確かめています

### モデル

- 2作目(storybot)のLLaMA方式GPTを引き継いでいます。dropoutなし、バイアスなし、埋め込みとLM headの重み共有なしです
- **Flash Attention**(`GPTConfig(attn_impl="flash")`): Dao et al. (2022) の方式を、FlashAttention-2のループ順でPyTorchの演算として実装しています(`torch.autograd.Function`)
  - 順伝播は、クエリのブロックごとにキーのブロックを順に見ていき、softmaxを「オンライン」で更新します(最大値・分母・出力を、最大値が増えるたびに補正します)。系列長×系列長のスコア行列は作りません
  - 逆伝播用に保存するのは、出力と各クエリのlogsumexpだけです。確率はブロックごとに計算し直します。因果マスクで全部隠れるブロックは、順伝播でも逆伝播でも飛ばします
  - KVキャッシュに対応しています(クエリがキーより短い場合、クエリは末尾の位置として扱います)
  - 計算はfloat32以上で行います。bf16のautocastの中でも、内側の行列積をbf16に落としません
- RMSNormの統計量、注意のsoftmax、RoPEの回転、MoEのルーター、損失のlog-softmaxは、bf16などの入力でもfloat32で計算します。float64の入力はfloat64のまま計算するので、テストでは実装どうしをfloat64で厳密に比べられます
  - 先頭の次元(バッチ・ヘッド)はブロードキャストできます。GQAのK/Vは複製せずに渡し、勾配は元の形に足し戻します
  - テストでは、出力と勾配を素朴な実装と比べています(float64で1e-10の精度)。ほかに、`gradcheck`、保存したlogsumexpが正確なこと、逆伝播用に保存されるテンソルに系列長の2乗の大きさのものがないこと、モデル全体の損失・勾配・KVキャッシュ付き生成が素朴な実装と一致することを確かめています
- **Grouped Query Attention**(`GPTConfig(n_kv_heads=...)`): Ainslie et al. (2023) の方式です。キー・バリューのヘッドをクエリより少なくし、連続する `n_heads / n_kv_heads` 個のクエリヘッドで1組のK/Vを共有します(クエリヘッド h はK/Vヘッド h ÷ グループの大きさ を使います)
  - 既定の `None` は `n_heads` と同じで、通常のMulti-Head Attentionです。`1` にするとMulti-Query Attentionになります
  - K/Vの射影とKVキャッシュが、グループの大きさの分だけ小さくなります。計算ではK/Vをグループ方向にブロードキャストし、クエリヘッドの数だけ複製することはしません。素朴な実装とFlash Attentionの両方で使えます
  - テストでは、「K/Vの重みをグループ内のヘッドに複製した通常のMulti-Head」と出力・勾配が一致すること(共有したK/Vの重みの勾配は、複製した分の合計になります)を確かめています。ほかに、KVキャッシュがK/Vヘッドの数だけで持たれること、パラメータの減り方、モデル全体で素朴な実装とFlash Attentionが一致することも確かめています
- **SDPA**(`GPTConfig(attn_impl="sdpa")`): PyTorchの融合カーネル `scaled_dot_product_attention` を使います。GPUではFlashAttentionなどのカーネルが使われ、このCPUでも最速でした。GQAは `enable_gqa` でK/Vを複製せずに渡します。KVキャッシュの後に複数のトークンをまとめて入れるときは、`is_causal=True` のマスク(クエリとキーの先頭がそろっている前提)が合わないので、位置から作ったマスクを渡します。テストでは、素朴な実装と出力・勾配がfloat64で一致すること、キャッシュの後に何トークンずつ入れてもキャッシュなしと一致することを確かめています
- **Mixture of Experts**(`GPTConfig(n_experts=..., moe_top_k=..., moe_aux_coef=...)`): 各ブロックのFFNを、E個のSwiGLU(専門家)とルーター(線形層)に置き換えます。各トークンは、ルーターの確率が高い上位k個の専門家だけを通り、その出力をゲートの重みで足し合わせます(Shazeer et al. 2017、Switch Transformer、Mixtral)
  - ゲートは、k=1ならルーターの確率そのもの(Switch方式。ルーターが本来の損失からも学べます)、k≥2なら上位k個の確率を合計1に正規化したもの(Mixtral方式)です
  - 容量の上限はなく、トークンを捨てることはありません。計算は専門家ごとにトークンをまとめて行います
  - 負荷分散の補助損失は、Switch Transformerの `E × Σ_i f_i × P_i` です(f_i は専門家 i に割り当てられた割合、P_i はルーター確率の平均)。振り分けが均等なら1で、偏るほど大きくなります。学習モード(`model.train()`)では、損失に `moe_aux_coef`(既定0.01)倍で足します。評価モードの損失は交差エントロピーだけです
  - `n_experts=0`(既定)なら、今までどおりの密なFFNです。`num_active_params()` で、1トークンが通るパラメータ数を数えられます
  - テストでは、出力・補助損失・全パラメータの勾配を「1トークンずつ上位k個を選んで足す素朴な実装」と比べています(float64で1e-10の精度)。ほかに、全専門家を同じ重みにすると密なFFNと一致すること、補助損失だけを下げる方向に学習すると偏っていた振り分けが実際に分散することを確かめています
- **コンテキスト長の拡張**(`extend_context(model, 新しい長さ, "pi" | "ntk" | "yarn")`): 学習した長さ L より長い文脈を扱えるように、RoPEの周波数を引き伸ばします。RoPEはパラメータを持たないので、重みはそのまま使い、位置の表だけを作り直します。倍率 s は「新しい長さ ÷ L」です。`GPTConfig` の `rope_scaling` / `rope_factor` / `rope_original_max_seq_len` でも指定できます
  - **PI**(Position Interpolation、Chen et al. 2023): 全ペアの周波数を 1/s にします。位置 m を m/s として読むので、どの位置も学習した範囲に収まります
  - **NTK-aware**: RoPEの底を base·s^(d/(d−2)) に上げます。最も速く回るペアはそのまま、最も遅いペアはちょうど 1/s になり、その間は遅いペアほど強く引き伸ばされます
  - **YaRN**(Peng et al. 2023): 学習した長さの中で何周するか(r = L ÷ 波長)でペアを分けます。32周を超える速いペアはそのまま、1周に満たない遅いペアはPIと同じく 1/s にし、その間は r に比例して両者を混ぜます。さらに、長い文脈で平らになりがちな注意を鋭くするため、ロジットに (0.1·ln s + 1)² を掛けます。ランプは論文の連続的な式で書いています(HuggingFaceの実装は次元を整数に丸めます)
  - テストでは、各方式の周波数と回転を「ペアごとにスカラーで計算した参照」と比べています。ほかに、PIでは位置 s·m が元の位置 m と同じ回転になること、YaRNでは速いペアが元のまま・遅いペアがPIと同じ・その間が両者の中間になること、注意のロジットが温度の分だけ大きくなること、どの方式でも注意が相対位置だけで決まる性質が保たれることを確かめています
- **torch.compile**(`compile_model(model)`): PyTorch 2のコンパイラーで、学習・評価の順伝播と逆伝播をまとめてコンパイルします(TorchDynamoがPythonのコードからグラフを取り出し、InductorがCPU向けのC++/OpenMPのコードを生成します)
  - InductorはC++コンパイラーを使います。Windowsでは、`cl.exe` が見つからなければ、Visual Studio Build Tools の `vcvars64.bat` の環境を自動でプロセスに読み込みます(`setup_compiler()`)
  - その場でコンパイルする(`nn.Module.compile`)ので、`state_dict` のキーはコンパイル前と同じで、チェックポイントをそのまま使い回せます
  - コンパイルされるのは `model(idx, targets)` の呼び出しだけです。`generate` は1トークンごとに形が変わるので、eagerのまま動きます
  - 素朴な実装・Flash Attention・GQA・MoEのどの構成でも、グラフは途切れず1つになります。MoEは、専門家ごとのトークン数で分岐しない書き方にし、データで決まる大きさをグラフに取り込む設定(`capture_scalar_outputs` など)を有効にしています
  - テストでは、各構成で学習の順伝播がグラフ1つになること、コンパイルした学習3ステップの損失と更新後の重みがeagerと一致すること(実際にコンパイルされ、eagerに戻っていないことも確認)、`state_dict`・評価時の損失・生成が変わらないことを確かめています

### 学習

- 2作目(storybot)の事前学習ループを引き継いでいます。AdamW(重み減衰は行列だけ)、D2Z(線形ウォームアップの後、最後のステップで0まで線形に下げる学習率)、混合精度、勾配クリップです。混合精度の自動選択は、CPUではfp32、GPUではbf16の演算器を持つ世代(Ampere以降)ならbf16、それより前(T4など)ならfp16です(`torch.cuda.is_bf16_supported()` はbf16をソフトウェアで代わりに計算できるだけのGPUでもTrueを返すので使いません)。チェックポイントには、モデル・オプティマイザー・スケジューラー・バッチの乱数まで保存するので、中断してから再開しても、中断しなかった場合と同じ結果になります
- **勾配累積**(`PretrainConfig(batch_size=B, grad_accum_steps=k)`): 1回の更新のバッチ B を k 個のマイクロバッチに分け、順に順伝播・逆伝播して勾配を足し合わせ、オプティマイザーの更新は1回だけ行います。メモリはマイクロバッチ1つ分で済みます
  - 各マイクロバッチの損失は、バッチに占める行数の割合で重み付けします。そのため、B が k で割り切れない場合(6行を4つに分けて2・2・1・1行など)も、勾配はバッチ全体の平均の損失の勾配と一致します
  - 勾配のクリップは、全マイクロバッチの勾配を足した後に1回だけ行います。fp16の損失スケーリングとも組み合わせられます
  - 引くバッチは k によらず同じです。したがって、勾配累積を使っても使わなくても、学習結果は(浮動小数点の誤差を除いて)同じになります
  - MoEの負荷分散の補助損失だけは、マイクロバッチごとに計算して平均します。振り分けの割合をマイクロバッチ単位で数えるので、累積しない場合とは少し違う値になります
  - テストでは、累積した勾配が大きなバッチ1回分の勾配とfloat64で一致すること(割り切れない分け方を含む)、モデルに渡るのがマイクロバッチの大きさだけであること、クリップが累積の後に1回だけ効くこと、事前学習を累積なし・4分割・8分割で回すと損失の履歴と最終的な重みが一致することを確かめています
- **勾配チェックポイント**(`GPTConfig(grad_checkpoint=True)`、Chen et al. 2016): 学習の順伝播で、各ブロックの中間の活性化を保存せず、ブロックの入力だけを残します。逆伝播のときにそのブロックの順伝播をもう一度計算し、その計算を通して勾配を求めます。順伝播が1回増える代わりに、活性化のメモリが層数×ブロック入力の大きさまで減ります
  - `torch.autograd.Function` で自作しています。逆伝播の中で、保存した入力からブロックを再計算し、その中で逆伝播します(reentrant方式)。パラメータの勾配は、この内側の逆伝播で `.grad` に足されます。そのため `loss.backward()` では使えますが、`torch.autograd.grad(loss, params)` では使えません
  - 逆伝播はautocastの外で走るので、順伝播のときの混合精度の状態を覚えておき、再計算でも同じ状態にします
  - MoEの負荷分散の補助損失はブロックの中で計算されるので、チェックポイントの出力に含めて、ルーターに勾配が届くようにしています。そのため、ブロックとMoEには、モジュールに何も書き込まずに結果を返す計算(`forward_pure`、`route`)を用意しました
  - 使うのは、勾配を計算する順伝播(KVキャッシュなし)のときだけです。評価や生成は通常どおりです。勾配累積とも組み合わせられます
  - torch.compileの中では、DynamoがこのFunctionの「逆伝播の中の逆伝播」をトレースできず、ブロックごとにグラフが途切れます。そのため、コンパイル中だけはPyTorchの `torch.utils.checkpoint`(non-reentrant方式)に切り替えます。どの構成でもグラフは1つのままです
  - テストでは、出力・入力の勾配・パラメータの勾配がチェックポイントなしとfloat64で一致すること、順伝播が逆伝播で1回だけ再計算されること、bf16のautocastの中でも勾配がビット単位で一致すること、モデルで逆伝播用に保存されるのが「1層あたりちょうどブロックの入力1つ分」になることを確かめています。ほかに、密・Flash+GQA・MoEの各構成で全パラメータの勾配が一致すること、勾配累積と組み合わせた事前学習が通常の学習と一致すること、torch.compileでグラフが途切れずeagerと一致することも確かめています
- **分散学習(データ並列)**: `launch(fn, プロセス数, 引数..., threads_per_rank=...)` で複数のプロセスを起動し、その中で `pretrain` を呼ぶと、データ並列で学習します。PyTorchの `DistributedDataParallel` は使わず、通信の基本操作(`broadcast` / `all_reduce`、CPU向けのglooバックエンド)だけを使って書いています
  - 各プロセス(rank)はモデル全体のコピーを持ちます。学習の始めに、rank 0の重みを全員に配ります
  - 毎回の更新で、全rankが同じ乱数で同じバッチを引き、それぞれ自分の担当の行(連続した、大きさの差が1以内の区間)だけで順伝播・逆伝播します。勾配累積は、この担当分をさらに分けます
  - 勾配は、各rankが「担当の行数 ÷ バッチの行数」を掛けてから合計(all-reduce)します。行数が割り切れなくても、バッチ全体の平均の損失の勾配になります。全rankが同じ勾配で同じ更新をするので、コピーはずれません。通信は、勾配を約25MBずつにまとめて、勾配累積の後に1回だけ行います。勾配のクリップは平均した勾配に対して行います
  - どのrankでも勾配がなかったパラメータ(どのトークンも来なかったMoEの専門家など)は、1プロセスのときと同じく勾配なしのままにします(AdamWがその重みに重み減衰をかけないように)
  - 評価は検証用のバッチを分担し、損失の合計を足し合わせます。ログとチェックポイントは rank 0 だけが書きます
  - MoEの負荷分散の補助損失は、勾配累積のときと同じく、rankごとに計算した値の平均になります
  - テストでは、実際に2〜3プロセスを起動して確かめています。違う初期値から始めても重みが揃うこと、8行を3プロセスに分けるような割り切れない場合も勾配がバッチ全体の勾配とfloat64で一致すること、2・3プロセス(勾配累積・MoEあり)での事前学習が1プロセスの学習と損失の履歴・最終的な重みまで一致すること、全rankの重みがビット単位で同じであること、各rankが担当の行と担当の評価バッチだけを処理していること、どのrankのエラーも呼び出し元に伝わることです
- **ZeRO**(`PretrainConfig(zero_stage=1 | 2)`、Rajbhandari et al. 2020): データ並列で各rankが重複して持っていた学習の状態を、rankの間で分担します。全パラメータを1本の平たいベクトル(重み減衰をかける行列が先、その他が後)とみなして、rankの数で均等な区間に分け、各rankは自分の区間だけを受け持ちます
  - **ステージ1**: AdamWの状態(1次・2次モーメント。パラメータの2倍の量)を、自分の区間の分だけ持ちます。勾配は通常のデータ並列と同じくall-reduceし、各rankが自分の区間だけを更新したあと、更新した区間をall-gatherして全員の重みをそろえます
  - **ステージ2**: 勾配も分担します。all-reduceの代わりにreduce-scatter(通信量は半分)で、自分の区間の合計済みの勾配だけを受け取り、元の勾配は捨てます
  - AdamWは要素ごとの計算なので、平たい区間で更新しても、パラメータごとに更新した場合と同じ結果になります。区間を「重み減衰をかける部分」と「かけない部分」の最大2つのテンソルに分けて持つので、重み減衰はこれまでどおり行列だけにかかります
  - 勾配のクリップは、各rankの区間の二乗和を合計した全体のノルムで行います
  - チェックポイントには、全rankから集めたオプティマイザーの状態を1本のベクトルとして保存します。そのため、保存したときと違うプロセス数・違うステージで再開できます
  - 重みはモデル側を正とし、更新のたびにモデルから自分の区間を取り直します(オプティマイザーを作った後に重みを読み込んでも反映されます)
  - 制限: どのrankでも勾配がなかったパラメータ(どのトークンも来なかったMoEの専門家)は、勾配0として更新されます(モーメントが減衰し、重み減衰もかかります)。パラメータごとのAdamWのように飛ばすことはできません。fp16の損失スケーリングとは組み合わせられません。ステージ3(パラメータ自体の分担)は実装していません
  - テストでは、1プロセスで通常のAdamWとfloat64で一致すること、3プロセスで各rankの状態がちょうど全体の1/3ずつになり、ステージ2では元の勾配が残らないこと、2・3プロセス(ステージ1・2、勾配累積あり)の事前学習が1プロセスの学習と一致し、保存した状態が1プロセスのAdamWのモーメントと一致すること、2プロセス・ステージ2で途中まで学習したものを3プロセス・ステージ1で再開しても中断しなかった学習と一致することを確かめています
- **Muon**(`PretrainConfig(optimizer="muon", muon_lr=0.02)`、Keller Jordan 2024): Transformerのブロック内の重み行列(注意の射影、FFN、MoEのルーターと専門家)を、勾配のモメンタムを直交化した方向に更新します。直交化は、行列の特異値をすべて1付近にそろえる操作で、勾配の中の少数の大きな方向だけでなく、あらゆる方向に同じくらいの歩幅で進むようにします
  - モメンタムはNesterov型(係数0.95)です。直交化はSVDではなく、5次のNewton-Schulz反復 X ← aX + b(XXᵀ)X + c(XXᵀ)²X(係数 3.4445, −4.7750, 2.0315)を5回かけます。この反復は特異値にだけ働き、フロベニウスノルムで正規化した特異値 s を a·s + b·s³ + c·s⁵ に写すことを繰り返して、およそ0.7〜1.2の範囲に集めます
  - 更新量は √max(1, 行数/列数) 倍します。q・k・vを1つにまとめた射影は、Q・K・Vの部分ごとに別々に直交化します
  - 埋め込み、出力の射影(LM head)、RMSNormのゲインは、同じオプティマイザーの中でAdamW(学習率は `peak_lr`)で更新します。1つのオプティマイザーなので、学習率のスケジュール・チェックポイント・勾配累積・データ並列はそのまま使えます。ZeROとは組み合わせられません(行列を区間で切ると直交化できないため)
  - テストでは、Newton-Schulzの結果が「SVDで取り出した特異値にスカラーの5次式を5回かけて組み立て直したもの」とfloat64で一致すること、実際に特異値が1付近に集まること、1ステップの更新が式どおりの参照(Muon側)と `torch.optim.AdamW`(AdamW側)に一致すること、埋め込みとLM headを固定してもMuonが更新する行列だけで損失が下がること、中断からの再開とデータ並列が通常の学習と一致することを確かめています
- **実験の記録(Weights & Biases)**(`PretrainConfig(wandb_project="...")`): 学習の設定(学習・モデルの設定、パラメータ数、プロセス数)を最初に1回、毎ステップの学習損失・その更新で使った学習率・処理したトークン数・1ステップの時間・トークン/秒を、評価のたびに検証損失とパープレキシティを記録します
  - 既定はオフラインモード(`wandb_mode="offline"`)です。記録は `wandb_dir`(既定は実行したディレクトリ)の `wandb/offline-run-*` にファイルとして残るだけで、外部には送信しません。後から `wandb sync <runのディレクトリ>` で送れます。`wandb_mode="online"` にすると wandb.ai に送ります(事前に `wandb login` が必要です)
  - データ並列では rank 0 だけが記録します。runのIDをチェックポイントに保存し、中断から再開したときは同じrunに続きのステップから記録します。学習が例外で止まっても、runは閉じます
  - `wandb_project` を指定しなければ、wandb は読み込みもしません
  - テストでは、呼び出しを記録する偽の wandb モジュールを使い、記録した学習損失・検証損失が学習の履歴と一致すること、学習率がD2Zの式どおりであること、再開時に同じrunのIDで続きのステップから記録されること、分散学習で rank 0 だけが記録することを確かめています。本物の wandb でも、オフラインモードでrunのファイルが作られることを確かめています

### データと検索

- **事前学習データ**(`scripts/prepare_data.py`): jawikiの各記事を「記事名、改行、段落を改行でつないだ本文」にし、記事の後ろに `<|endoftext|>` を入れて、トークン列のファイル(`train.bin` / `val.bin`)にします。曖昧さ回避ページは除きます。記事IDから決まる約1%の記事を検証用に取り分けます(シャードの順番によらず、シャードを増やしても同じ記事が検証側に入ります)。トークナイザーは学習用記事の先頭2,000万字で学習したBPE(語彙16,000)です
- **検索器**(`scripts/build_index.py`): 段落を単位にしたBM25です。スコアはLuceneと同じ形(idfは ln(1 + (N − df + 0.5)/(df + 0.5))、k1 = 1.2、b = 0.75)です。日本語は単語の区切りがないので、索引の語は正規化(NFKC・小文字化)した文字bigram(2文字ずつ、空白はまたがない)にし、段落の本文の前に記事名と節の見出しを付けて索引します。転置索引は語ごとの(文書ID、出現回数)をCSR形式のnumpy配列で持ち、検索は語ごとの寄与をベクトル演算で足し合わせます
- **検索の評価**(`scripts/eval_retrieval.py`): auto-wiki-qaの質問を検索し、上位k件に「質問の根拠になった段落」(同じ記事で、根拠の文章と重なる段落)があるか(gold@k)と、「答えの文字列を含む段落」があるか(answer@k。抜き出し型で答えるにはこちらが必要)を数えます
- テストでは、BM25のスコアを「文書ごと・語ごとに式どおり計算する素朴な実装」とランダムなコーパスと k1・b で比べています。ほかに、珍しい語ほど効くこと、同じ出現回数なら短い文書が上に来ること(b = 0 なら同点)、出現回数の効きが頭打ちになること、上位k件が同点を含めて全件の並べ替えと一致すること、事前学習データを復号すると元の記事が区切りトークン付きでそのまま戻ること、評価の数え方が手計算と一致することを確かめています

### SFT(検索→読む→答える)

- 1つのやり取りを、特殊トークンで区切った次の並びにします。モデルが書くのは検索(`<|search|>`〜`<|/search|>`)と答え(`<|answer|>`〜`<|endoftext|>`)で、質問と段落は外から与えます。損失は、モデルが書くトークンにだけかけます(それ以外の正解ラベルは −100 にして交差エントロピーから外します)

  ```
  <|question|>質問<|search|>検索語<|/search|><|doc|>記事名 / 見出し⏎段落<|/doc|>…<|answer|>答え<|endoftext|>
  ```

- 区切りの特殊トークンはIDを直接入れ、質問や段落の文はふつうの文字としてエンコードします。Wikipediaの本文に `<|doc|>` のような文字列があっても、特殊トークンにはなりません。学習と推論は同じ関数で部分ごとにエンコードするので、トークンの切れ方がそろいます
- 例は auto-wiki-qa の質問から作ります。検索語は当面、質問そのものです(BM25は質問文のままでもよく当たります)。段落は、質問でBM25を引いた上位3件(1件400字まで)です。推論のときも同じ検索器で引くので、学習と本番の条件がそろいます。答えの文字列が3件のどれかに含まれる質問だけを使い、段落から答えを抜き出す形に寄せます
- 分割は記事単位です。評価用は、事前学習で検証用に取り分けた記事(約1%)の質問なので、事前学習でもSFTでも見ていない記事について、段落を読んで答えられるかを測れます。SFTの検証用は別の約1%の記事、残りが学習用です
- TPUでも動きます(PyTorch/XLA)。`--device auto` はCUDA、なければTPU、なければCPUを選びます。XLAは計算をため込んで1つのグラフにまとめてから実行するので、1ステップの終わりにだけ同期し(損失の値を読むのも1回)、SFTのバッチ幅は128の倍数に切り上げてグラフの種類を減らします。形が1トークンごとに変わる生成はCPUに移して行い、チェックポイントはCPUに移してから保存します。混合精度はbf16です
- 学習ループは事前学習と同じ部品(AdamW、D2Z、混合精度、勾配クリップ、勾配累積、チェックポイントと中断からの再開)を使い、長さの違う例をバッチの中で `<|pad|>` で詰めます。勾配累積では、損失はマイクロバッチごとの平均です
- **推論ループ**(`scripts/ask.py`、`scripts/eval_e2e.py`): `<|question|>質問<|search|>` まで入れてモデルに `<|/search|>` まで書かせ、書いた検索語でBM25を引き、上位k件の段落と `<|answer|>` を続けて答えを書かせます。検索語が空のとき(ほかの特殊トークンが先に出たときも含む)は、質問で検索します
- テストでは、損失をかけるトークンがちょうど検索と答えの部分になること、損失が「書く部分だけを1つずつ計算した参照」と一致すること、小さなモデルをSFTすると学習した質問に正しい答えを生成できるようになること(学習前は0問)、中断から再開したSFTが中断しなかった場合と一致すること、評価用の記事が事前学習で取り分けた記事とちょうど一致することを確かめています

**注意機構の速度とメモリ**: CPU(i7-13700F、16スレッド)で順伝播と逆伝播を測りました。条件は、バッチ1・ヘッド8・ヘッド次元32・float32・因果マスクありです。メモリは、各条件を別プロセスで実行したときのピークの増分です。

| 系列長 | 素朴な実装 | Flash Attention(自作、ブロック128) | PyTorchの `scaled_dot_product_attention` |
|---|---|---|---|
| 256 | 1.4ms / +46MB | 3.9ms / +46MB | 1.4ms / +41MB |
| 512 | 3.9ms / +72MB | 8.3ms / +49MB | 4.0ms / +47MB |
| 1024 | 27ms / +142MB | 35ms / +52MB | 12ms / +63MB |
| 2048 | 122ms / +441MB | 130ms / +60MB | 37ms / +65MB |
| 4096 | 643ms / +1,655MB | 484ms / +73MB | 96ms / +80MB |

- メモリは、素朴な実装が系列長の2乗で増えるのに対し、Flash Attentionはほぼ線形でした
- 速度は、自作のFlash Attentionがブロックごとに Python のループを回すため、短い系列では素朴な実装より遅いです(256で約2.8倍)。素朴な実装を上回ったのは4096からでした。PyTorch組み込みの融合カーネル(SDPA)は、どの長さでも最速でした
- ブロックの大きさは、系列長1024のとき、32で247ms、64で74ms、128で35ms、256で24ms、512で25msでした。大きいほどループの回数が減って速くなる一方、メモリは増えます

**コンテキスト長の拡張**: webbotにはまだ学習済みモデルがないので、2作目(storybot)の学習済みモデル(約900万パラメータ、256トークンの窓で学習、ヘッド次元32)を同じ構造のこのGPTに読み込んで測りました。評価は、storybotの検証データから長さNの窓を取り、合計約6.5万トークンについて、位置の区間ごとに平均した損失です。TinyStoriesは1話が短く、長い窓には複数の話が区切りトークンをはさんで入るので、「長い文脈を活かせるか」より「学習した長さを超えても崩れないか」を見る評価です。

追加学習なし(zero-shot)の全位置の平均損失です。学習した長さ(N=256)では2.238でした。

|---|---|---|---|---|
| 512(2倍) | 2.502 | 2.429 | **2.256** | 2.269 |
| 1,024(4倍) | 2.960 | 2.822 | 2.506 | **2.422** |

  |---|---|---|---|---|---|---|
  | 検証損失 | 5.017 | 3.882 | 3.570 | 3.391 | 3.205 | **3.152**(PPL 23.4) |

  生成は、Wikipediaらしい文体の自然な日本語になりましたが、内容は誤りが多く(「日本の首都は福岡である。」)、同じ語の繰り返しも目立ちます

- **SFT**: 上のモデルから、学習用84,444問で6,000ステップ(1ステップ32問、学習用を約2.3周)学習しました。検証用の損失(モデルが書く部分のトークンの平均)は0.288(500ステップ)→0.215(6,000ステップ)でした
- **評価**: 事前学習でもSFTでも見ていない記事についての評価用878問に、BM25の上位3件の段落を与えて答えさせると、**答えの完全一致は54.3%**、答えの文字列を含む回答は59.5%でした
  - 評価用は「上位3件に答えが含まれる質問」だけなので、この数字は段落を読んで答えを抜き出す力を表します。検索で答えの入った段落が引けない質問(全体の約19%)を含めた、検索から答えまでの正答率は、およそ0.81×0.543 ≈ 44% と見積もれます(直接は測っていません)
  - 誤りには、段落の別の語句を答えたもの(「ダムはどこ？」に「三芳水道企業団」)や、長い答えの途中を崩したもの(「祈りのもとで:脱同性愛運動生したもの(英語版)」)がありました

**推論ループ(検索から答えまで)**: SFTしたモデルを手元(CPU)で動かし、モデル自身が `<|search|>` の後に検索語を書き、その検索語でBM25を引いて、上位3件を読ませて答えさせました。評価用の記事についての全1,082問(検索で答えが引けない質問も含む)の結果です。

| 検索語 | 完全一致 | 答えを含む | 引いた段落に答えあり | 検索語が質問と同じ | 1問あたり |
|---|---|---|---|---|---|
| モデルが書いた検索語 | 43.7% | 47.8% | 79.9% | 84.0% | 0.43秒 |
| 質問そのもの | 44.1% | 48.2% | 81.1% | 100% | 0.19秒 |

- 検索から答えまでの完全一致は約44%で、SFTの評価(段落に答えがある問題で54.3%)と検索の当たり率(約81%)から見積もった値とほぼ同じになりました
- モデルは検索語として質問を書き写すように学習しましたが、16%の質問では書き写しが崩れます(珍しい漢字が別の文字になるなど。「阿久澤 騰」→「阿久澤 岩メ」)。そのぶん段落の当たり率が1.2ポイント下がり、正答率は質問をそのまま使う場合をわずかに下回りました。今のところ、モデルに検索語を書かせる利点は出ていません(SFTデータの検索語が質問そのものなので、当然の結果でもあります)
- 検索の対象は1シャード(6.4万記事)だけなので、それ以外の記事についての質問(例: 「富士山の高さは？」)には答えられません

**JSQuAD**(`scripts/eval_jsquad.py`): JGLUEのJSQuAD v1.3 の検証用(59記事・4,442問、CC BY-SA 4.0)で、問題に付いている段落を1件だけ `<|doc|>` として与えて答えさせました。JSQuADでは学習していません(auto-wiki-qaでのSFTのまま)。採点はSQuADと同じ形で、全角・半角と空白の違いを無視し、複数ある正解のうち一番近いものと比べます。

| 完全一致 | 文字単位のF1 | 答えを含む | 1問あたり |
|---|---|---|---|
| 36.5% | 50.8% | 47.5% | 0.10秒 |

- JSQuADの学習用(62,697問)をSFTデータに加えて学習し直すこともできます(`scripts/add_jsquad.py`、`scripts/run_pipeline.py --jsquad`)。問題に付いている段落を1件だけ `<|doc|>` にし、1つ目の正解を答えにします。検証用・評価用はauto-wiki-qaのままなので、混ぜたことでauto-wiki-qaの成績が下がらないかも比べられます
- auto-wiki-qaの評価用(完全一致54.3%)より大きく下がりました。人が書いた質問は、段落と言い回しが違うものや、「どこか」「何季か」のように答えの種類で絞り込む必要があるものが多く、段落の中の別の語句を抜き出す誤りが目立ちます(「日本で梅雨がないのは北海道とどこか。」に「雨季」、「梅雨とは何季の一種か?」に「5月から7月」)

## セットアップ

Windows・Python 3.12で動作を確認しています。Rust版のビルドには、Rust(MSVCツールチェーン)と Visual Studio Build Tools(C++)が必要です。torch.compile にも Visual Studio Build Tools(C++)を使います(環境変数は自動で読み込むので、開発者用のシェルから起動する必要はありません)。C++コンパイラーがない環境では、torch.compile のテストはスキップされます。

```
python -m venv .venv
.venv\Scripts\pip install torch --index-url https://download.pytorch.org/whl/cpu
.venv\Scripts\pip install -r requirements.txt
.venv\Scripts\maturin develop --release -m rust/Cargo.toml
.venv\Scripts\python -m pytest tests
```

Rust版をビルドしなくても、Python版だけで動きます(`backend="python"`)。ただし、Rust版のテストは失敗します。

**KaggleのTPUで全段階を自動で実行する**: `python scripts/kaggle_submit.py` で、`kaggle/pipeline_kernel.py` を今のコミットに固定してKaggleに提出し、TPU v5e-8(の1チップ)で実行させます(Kaggle CLIと `~/.kaggle/kaggle.json` が必要です。コミットはGitHubにプッシュ済みである必要があります)。カーネルはまず全段階を小さな設定で数分ずつ試し、通ったら本番に入ります。途中で止まったら `--continue` を付けて提出し直すと、前回の出力から続きを再開します。`--accelerator NvidiaTeslaT4` でGPUでも動きます。

**Kaggleのノートブックで全段階を自動で実行する**: Kaggleで [notebooks/kaggle_pipeline.ipynb](notebooks/kaggle_pipeline.ipynb) を読み込み、Accelerator を GPU(T4 x2 または P100)、Internet を On にして、「Save Version」→「Save & Run All (Commit)」で実行します。実行はKaggleのサーバーで続くので、ブラウザもPCも閉じてかまいません。`scripts/run_pipeline.py` がデータの準備(jawiki全22シャードのダウンロードを含む)→ 事前学習 → 検索の索引 → SFTデータ → SFTと評価を順に行い、結果はノートブックの Output に出ます。Kaggleの1回の上限(12時間)より前に学習を止めて正常に終わるので、続きは前回の出力を入力に追加して実行し直せば再開します。

**Google Colabで事前学習する**: [notebooks/pretrain_colab.ipynb](https://colab.research.google.com/github/KoRo2222/tiny-gpt-librarian/blob/master/notebooks/pretrain_colab.ipynb) を開き、ランタイムを T4 GPU にして上から順に実行します。jawikiのダウンロードとデータの準備はColabの上で行い、トークン列のファイルとチェックポイントは Googleドライブ(`MyDrive/webbot/`)に保存します。接続が切れたら同じ手順で実行し直すと、チェックポイントの続きから再開します。最初に50ステップの試運転をして、1ステップの時間から学習全体の時間の見込みを表示します。

事前学習が終わったら、[notebooks/sft_colab.ipynb](https://colab.research.google.com/github/KoRo2222/tiny-gpt-librarian/blob/master/notebooks/sft_colab.ipynb) でSFTします。SFTデータの作成もColabの上で行います。

手元で学習するときは、次のようにします(`--resume` を付けておけば、中断した後に同じコマンドで続きから再開します)。

```
.venv\Scripts\python scripts\pretrain.py --data data/jawiki --out runs/base --steps 20000 --resume
```

データは Hugging Face から parquet をダウンロードして置きます(`data/` 以下は git の管理外です)。

```
data/raw/jawiki/        hpprc/jawiki の data/train-*.parquet(1ファイル約0.4GB、全22ファイル)
data/raw/auto-wiki-qa/  cl-nagoya/auto-wiki-qa の data/train-*.parquet(全4ファイル、記事ID順)
data/raw/jsquad/        JGLUE の datasets/jsquad-v1.3/{train,valid}-v1.3.json

.venv\Scripts\python scripts\prepare_data.py     # data/jawiki/ に tokenizer.json, train.bin, val.bin
.venv\Scripts\python scripts\build_index.py      # data/index/ に検索索引
.venv\Scripts\python scripts\eval_retrieval.py   # 検索の評価
```
