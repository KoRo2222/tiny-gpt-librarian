# webbot

日本語Wikipediaを検索し、見つけた文章を読んで質問に答える小さな言語モデル(RAG)を、トークナイザーからすべて自前で実装するプロジェクトです。LLM自作シリーズの3作目です。

## 概要

- **検索→読む→答える**: ローカルに置いたWikipediaの段落を検索し、取り出した段落から答えを抜き出して回答するモデルを目指します
- **データ**: 文書は [hpprc/jawiki](https://huggingface.co/datasets/hpprc/jawiki)(段落単位の日本語Wikipedia、CC BY-SA 3.0 / GFDL)、学習用のQAは [cl-nagoya/auto-wiki-qa](https://huggingface.co/datasets/cl-nagoya/auto-wiki-qa)(同じWikipediaから生成された質問・答え・根拠段落、CC BY-SA 4.0)、評価は [JSQuAD](https://github.com/yahoojapan/JGLUE)(CC BY-SA 4.0)を使う予定です
- **CPUのみ**で学習できる規模を前提にしています

## 構成

```
src/webbot/tokenizer/
  pretokenize.py   事前トークン化(文字種の境目で分割)と、コーパス全体の数え上げ(並列化可)
  base.py          全トークナイザー共通の部分(特殊トークン、encode / decode)
  bpe.py           バイトレベルBPE(Python版の参照実装と、Rust版の呼び出し)
  unigram.py       Unigram言語モデル(SentencePiece方式、バイトフォールバック付き)
rust/              BPEの学習とエンコードのRust実装(PyO3 + maturin、モジュール名 webbot_bpe)
tests/             テスト
```

### トークナイザー

2種類あります。どちらも同じ事前トークン化と同じ特殊トークンを使い、`train` / `encode` / `decode` / `save` / `load` の使い方も共通です。`len(tok)` は特殊トークンを含めた語彙数で、モデルの埋め込みの行数になります。

- **事前トークン化**: 日本語に対応しています。ひらがな・カタカナ・漢字・英字・数字・記号といった文字種の境目で分割し、ピース(トークン)がこの境目をまたぐことはありません
- **特殊トークン**は8個あり、通常の語彙の直後に次の順でIDを振ります。`vocab_size` は、特殊トークンを含めた語彙の総数です

  | トークン | 役割 |
  |---|---|
  | `<\|endoftext\|>` | 文書の区切り、回答の終わり |
  | `<\|pad\|>` | バッチの詰め物 |
  | `<\|question\|>` | 質問の始まり |
  | `<\|search\|>` 〜 `<\|/search\|>` | モデルが書く検索語 |
  | `<\|doc\|>` 〜 `<\|/doc\|>` | 検索で取り出した段落(1件ずつ) |
  | `<\|answer\|>` | 回答の始まり |

  想定している並びは `<|question|>質問<|search|>検索語<|/search|><|doc|>段落<|/doc|>…<|answer|>回答<|endoftext|>` です。特殊IDにするのは `encode(text, allowed_special=...)` で許可したトークンだけです。Wikipedia本文などに同じ文字列が出てきても、普通の文字としてエンコードします

#### BPE(`BPETokenizer`)

- GPT-2方式のバイトレベルBPEです
- 学習には2つの実装があり、`BPETokenizer(backend=...)` で選べます。既定の `"auto"` は、Rust版が入っていればRust版を使います
  - `"python"`: 参照実装。ペア頻度を差分更新し、ヒープは遅延削除方式です
  - `"rust"`: 同じ手順をRustで実装したものです。差分更新は、マージした位置の前後のペアだけを更新します
- 両者は、同点の決め方(記号の文字列の辞書順で大きい方を優先)まで含めて同じマージ列を出します
- エンコードもRust版があり、単語単位のキャッシュを持ちます。事前トークン化(正規表現)はPythonのままです
- テストでは、学習結果を「マージごとに全ペアを数え直す素朴な実装」と、Rust版の学習とエンコードの結果を「Python版」と、それぞれ完全一致で比べています

#### Unigram言語モデル(`UnigramTokenizer`)

- Kudo (2018) の方式で、SentencePieceの `unigram` に当たります。各単語を「ピースの対数確率の和が最大になる分割」で区切ります(Viterbi)
- 学習の流れ
  1. 頻出の部分文字列(最大16文字、「頻度×長さ」の上位100万個)から、大きな候補語彙を作ります
  2. EMでピースの確率を推定し直します。前向き・後ろ向きアルゴリズムで期待出現回数を求め、M-stepは最尤推定です
  3. 除いても尤度が下がりにくいピースから25%ずつ刈り込みます。損失の近似はSentencePieceと同じです
  4. 2と3を、予算の1.1倍以下になるまで繰り返します。最後に確率の高い順に予算まで残します
- **文字単位**で扱います。出現の99.95%をカバーする文字は必ず語彙に残し、それ以外のまれな文字はUTF-8のバイト(ID 0〜255)に分解します(バイトフォールバック)。どんな文字列も元に戻せます
- コーパスが小さく候補が予算に届かない場合、語彙は `vocab_size` より小さくなります
- テストでは、ViterbiとEMの期待出現回数を「全分割の列挙」と比べています。ほかに、EMで尤度が下がらないこと、使われないピースから先に刈り込まれること、予算がぎりぎりでも必須文字が残ることを確かめています

## 現状

トークナイザーまで実装済みです。

**BPEのPython版とRust版**: jawikiの1シャード(6.2万記事、4,800万字)で比べました(i7-13700F)。

| | Python版 | Rust版 |
|---|---|---|
| 学習 1,000万字・語彙8,000 | 54.8秒 | 2.1秒 |
| 学習 4,800万字・語彙16,000 | 212.5秒 | 10.9秒 |
| 学習時のメモリのピーク(4,800万字) | 3.5GB | 1.3GB |
| エンコード | 約12万トークン/秒 | 約300万トークン/秒 |

- 学習の時間には、8プロセスでの事前トークン化も含みます
- 学習したマージ列とエンコード結果は、どちらの条件でもPython版と完全に一致しました
- 語彙16,000のとき、1トークンは平均約1.7文字です

**BPEとUnigramの比較**: 語彙8,000で、学習に使っていない記事100万字の圧縮率を比べました。

| 学習データ | | 学習時間 | 1トークンあたりの文字数 | エンコード |
|---|---|---|---|---|
| 100万字 | BPE(Rust) | 0.5秒 | 1.53 | 約430万トークン/秒 |
| | Unigram(Python) | 16秒 | 1.43 | 約200万トークン/秒 |
| 1,000万字 | BPE(Rust) | 1.9秒 | 1.56 | 約420万トークン/秒 |
| | Unigram(Python) | 202秒 | 1.50 | 約150万トークン/秒 |

- 圧縮率はBPEのほうが良い結果でした。ただし、学習データを増やすと差は縮まりました(7%→4%)
- Unigramは必須文字(100万字で約3,300字)だけで語彙の予算の4割強を使います
- Unigramの学習はPythonのみの実装で、BPE(Rust)より2桁遅いです

検索器・モデル・学習はこれから実装します。

## セットアップ

Windows・Python 3.12で動作を確認しています。Rust版のビルドには、Rust(MSVCツールチェーン)と Visual Studio Build Tools(C++)が必要です。

```
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
.venv\Scripts\maturin develop --release -m rust/Cargo.toml
.venv\Scripts\python -m pytest tests
```

Rust版をビルドしなくても、Python版だけで動きます(`backend="python"`)。ただし、Rust版のテストは失敗します。
